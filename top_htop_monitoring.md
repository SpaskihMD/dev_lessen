```markdown
# 📊 Мониторинг в Linux: от простого к реальным задачам

Мониторинг — это наблюдение за состоянием системы: CPU, память, диски, сеть, процессы. Без этого невозможно понять, почему сервер тормозит, где утечка памяти или кто нагружает диск.

## 🧱 Базовые команды — "скорая помощь" администратора

### 1. `top` / `htop` — общая картина в реальном времени

```bash
top                    # классический
htop                   # красивее, удобнее (нужно установить: sudo apt install htop)
```

**Что видим:**
- Загрузку CPU (по ядрам)
- Использование RAM
- Список процессов с сортировкой по CPU (по умолчанию)

**Горячие клавиши в `top`:**
- `P` — сортировка по CPU
- `M` — сортировка по памяти
- `q` — выход
- `k` — убить процесс (ввести PID)

**Реальный пример:** Сервер стал медленно отвечать. Запускаем `top` — видим процесс `java` жрёт 200% CPU. Нажимаем `k`, вводим PID — проблема решена за 10 секунд.

### 2. `htop` — удобнее для человека

- Можно тыкать стрелочками
- `F6` — сортировка по любому столбцу
- `F9` — убить процесс
- Дерево процессов (`F5`)

### 3. `free -h` — память

```bash
free -h               # человеко-читаемый формат
              total   used   free   shared   buff/cache   available
Mem:           7.7G   2.1G   1.2G    234M       4.4G        5.1G
Swap:          2.0G    0B    2.0G
```

**Важно:** Смотреть на `available` — это реально доступная память. `free` может быть маленьким — это нормально (кэширование).

### 4. `df -h` — диски

```bash
df -h                 # свободное место на всех разделах
df -h /var/log        # только нужный раздел
```

**Реальный пример:** Сайт выдаёт 500-ю ошибку. `df -h` показывает `/dev/sda1` заполнен на 100%. Оказывается, лог-файлы съели всё место. Чистим `/var/log` — сайт оживает.

### 5. `du -sh *` — кто съел место

```bash
du -sh *              # размер каждой папки/файла в текущей
du -sh /var --max-depth=1   # проверить /var на 1 уровень вглубь
```

**Реальный пример:** Диск заполнился. `du -sh /var/*` показывает, что `/var/log/nginx` весит 50 ГБ. Заходим туда, удаляем старые логи.

### 6. `iostat` — дисковая активность

```bash
sudo apt install sysstat    # если нет
iostat -x 2                # каждые 2 секунды, расширенный вывод
```

Обратить внимание на:
- `%util` — утилизация диска (>80% — диск работает на пределе)
- `await` — время ожидания операций (>20 мс — тормоза)

**Реальный пример:** База данных тормозит. `iostat -x 1` показывает `%util = 100%` и `await = 150 мс`. Диск не справляется — нужен SSD или оптимизация запросов.

### 7. `netstat` / `ss` — сетевые соединения

```bash
ss -tulpn             # все слушающие порты (какие сервисы запущены)
ss -tunap             # все активные соединения
netstat -i            # статистика по интерфейсам (ошибки, коллизии)
```

**Реальный пример:** Сайт недоступен на 80-м порту. `ss -tulpn | grep :80` ничего не выдаёт. Значит, веб-сервер не запущен или сломался.

### 8. `dstat` — всё в одном

```bash
sudo apt install dstat
dstat                  # CPU, диск, сеть, своп — всё сразу
dstat -cdnm            # только CPU, диск, сеть, память
```

## 🔥 Реальные сценарии (туториалы)

### Сценарий 1. "Сервер тормозит, но непонятно почему"

**Пошагово:**

```bash
# 1. Смотрим общую картину
top
# Видим: CPU загружен, но не понятно кем

# 2. Смотрим нагрузку за последнее время
uptime                 # load average: 1, 5, 15 минут
# Если load average > количества ядер — перегруз

# 3. Смотрим ввод-вывод диска
iostat -x 1 5          # 5 раз с интервалом 1 сек
# Если %util близок к 100% — проблема в диске

# 4. Смотрим память
free -h
# Если available близко к 0 — нехватка памяти

# 5. Проверяем swap
swapon --show          # есть ли swap
vmstat 1 5             # si/so > 0 — память закончилась, идёт свопинг
```

**Диагноз:** Чаще всего тормоза — либо диск (I/O wait), либо память (swap), либо процесс-монстр.

### Сценарий 2. "Нашёл процесс-убийцу. Что с ним делать?"

```bash
# Узнать подробности о процессе (PID = 1234)
ps aux | grep 1234
ls -l /proc/1234/exe   # показать, откуда запущен
cat /proc/1234/cmdline # полная команда запуска
lsof -p 1234           # какие файлы открыты

# Принять решение:
kill 1234              # мягкое завершение
kill -9 1234           # жесткое (если не отвечает)
renice -n 19 -p 1234   # понизить приоритет (CPU), чтобы не мешал
```

### Сценарий 3. "Диск заполняется. Найти виновника"

```bash
# Шаг 1. Какой раздел?
df -h

# Шаг 2. Идём в самый большой раздел (например /var)
cd /var
du -sh * | sort -h     # сортируем по размеру

# Шаг 3. Заходим в самую большую папку и повторяем
cd /var/log
du -sh * | sort -h

# Шаг 4. Нашли огромный файл (например nginx/access.log.1)
# Что делать?
> nginx/access.log.1   # очистить не удаляя (чтобы не ломать дескрипторы)
# Или
truncate -s 0 nginx/access.log.1

# Настроить logrotate, чтобы такого больше не было
```

### Сценарий 4. "Сеть медленная или пакеты теряются"

```bash
# 1. Проверка потерь и задержек до сервера
ping -c 100 yandex.ru | grep loss
ping -c 100 8.8.8.8

# 2. Трассировка маршрута (где теряются пакеты)
mtr -r google.com      # лучший инструмент (mtr = ping + traceroute)
traceroute google.com

# 3. Сколько соединений и кто именно
ss -tan | wc -l        # общее число соединений
ss -tan state ESTABLISHED | wc -l   # активных

# 4. Какая программа открыла 1000 соединений?
sudo lsof -i | grep ESTABLISHED | awk '{print $1}' | sort | uniq -c | sort -n
```

### Сценарий 5. "Что-то жрёт процессор. Но не постоянно"

```bash
# Поймать процесс, который нагружает CPU раз в минуту
top -b -d 1 | grep -v "load"   # пакетный режим
# Или использовать sar (исторический сбор)
sudo apt install sysstat
sar -u 1 60                    # CPU каждую секунду, минуту

# Найти периодическую задачу
crontab -l                     # пользовательские
ls -la /etc/cron*              # системные
systemctl list-timers          # systemd таймеры
```

## 📈 Инструменты для долгосрочного мониторинга

Для продакшена нужны не разовые команды, а системы:

| Инструмент | Назначение |
|------------|------------|
| **Prometheus + Grafana** | Сбор метрик, красивые графики |
| **Zabbix** | Классика, оповещения (алерты) |
| **Netdata** | Красивые графики "из коробки" |
| **Nagios / Icinga** | Проверки работоспособности |
| **ELK (Elasticsearch + Logstash + Kibana)** | Логи + графики |
| **htop/glances** | Интерактивный мониторинг на сервере |

## 🧰 Быстрая шпаргалка

| Что нужно узнать | Команда |
|------------------|---------|
| Загрузка CPU сейчас | `top -bn1 \| grep "Cpu(s)"` |
| Свободная память | `free -h \| grep Mem` |
| Свободное место на диске | `df -h` |
| Самые жирные папки | `du -sh /* 2>/dev/null \| sort -h` |
| Кто слушает порт 80 | `ss -tulpn \| grep :80` |
| Сколько процессов | `ps aux \| wc -l` |
| Пинг до сервера | `ping -c 5 google.com` |
| Дисковый I/O | `iostat -x 1` |
| Сетевые соединения | `ss -tan state established` |
| Детали процесса | `lsof -p PID` |

## 🔁 Создание простого алерта (bash-скрипт)

```bash
#!/bin/bash
# alert.sh — присылает уведомление, если CPU > 80%

CPU_USAGE=$(top -bn1 | grep "Cpu(s)" | awk '{print $2}' | cut -d'%' -f1)
THRESHOLD=80

if (( $(echo "$CPU_USAGE > $THRESHOLD" | bc -l) )); then
    echo "⚠️ Высокая загрузка CPU: $CPU_USAGE%" | mail -s "Alert: CPU" admin@example.com
fi
```

Добавить в cron: `*/5 * * * * /home/user/alert.sh`

## 📚 Итог: стратегия диагностики

1. **Общая картина** — `top`, `htop`, `uptime`
2. **Узкое место** — CPU, память, диск, сеть (смотрим, что в красной зоне)
3. **Детали** — `ps`, `lsof`, `ss` для конкретного процесса
4. **История** — `sar`, логи, `journalctl -xe`
5. **Решение** — убить, рестартнуть, добавить ресурсов, оптимизировать

## 💡 Золотое правило

> **Прежде чем что-то менять — убедись, что понял причину.**  
> Не перезагружай сервер, не проверив логи. Не убивай процесс, не узнав, что это.
